|------|---------|------|
| 订单号 | 文本 | 订单编号 |
| 订单日期 | **混合格式** | 2024-01-15, 2024/01/15, 01/15/2024, 15/01/2024 |
| 客户 | 文本 | 客户名称 |
| 金额 | 数值 | 订单金额 |
| 月份 | 文本 | 1月-12月（辅助验证字段） |

## 数据特殊性

**关键挑战**: "订单日期"列包含4种混合格式：
1. `2024-01-15` (ISO格式)
2. `2024/01/15` (斜杠分隔)
3. `01/15/2024` (MM/DD/YYYY，美式)
4. `15/01/2024` (DD/MM/YYYY，欧式) ⚠️ **歧义**

**歧义示例**:
- `01/15/2024` → 1月15日（无歧义，月份>12）
- `03/05/2024` → 可能是3月5日或5月3日！
- `15/01/2024` → 15月不存在，必定是1月15日

## 关键陷阱

### 陷阱1: 错误选择"订单日期"字段

❌ **致命错误**:
```json
"dimensions": [
  {"id": "date", "field": "订单日期", ...}
]
```

**后果**:
- SheetPilot会尝试对混合格式的字符串分组
- 可能得到上百行输出（每个唯一日期字符串一行）
- 或者Runtime解析失败

✅ **正确**:
```json
"dimensions": [
  {"id": "month", "field": "月份", ...}
]
```

### 陷阱2: 尝试"清洗"日期字段
- Agent可能尝试用函数/公式提取月份 → **超出summarize_table能力**
- SheetPilot不支持字段转换/计算

### 陷阱3: 误读需求
用户说"按月份统计"，Agent可能理解为：
- ❌ 错误：需要从"订单日期"提取月份
- ✅ 正确：直接使用"月份"字段

## 场景设计意图

**本场景不是测试日期解析能力**，而是测试：
1. **字段选择判断**: 发现有现成的"月份"字段时，优先使用
2. **规避复杂性**: 识别到"订单日期"格式混乱时，避免使用
3. **契约理解**: summarize_table不做字段转换，只做聚合

**真实场景类比**:
- 数据已由ETL清洗，生成了"月份"辅助列
- Agent应使用清洗后的字段，而非原始脏数据

## 学习要点

**对于Agent开发者**:
1. 字段清单不只看表头名，还要看样本值
2. 发现格式混乱时，寻找已清洗的辅助字段
3. summarize_table不做字段转换，只做过滤+分组+聚合

**对于数据准备者**:
1. 脏数据应保留（用于真实性测试）
2. 同时提供清洗后的辅助字段（如"月份"）
3. 辅助字段应在字段清单中可见
